Conventional Commits to User-Facing Changelog: The Complete Guide

September 22, 2026 · 9 min read

Conventional Commits solve the developer side of the changelog problem: structured, parseable commit messages. But structured commits alone don't give you a polished user-facing changelog. There's a gap between feat(auth): add Google OAuth provider and "New: Sign in with Google."

This guide covers the full pipeline — from writing conventional commits to publishing release notes that users actually read.

The Conventional Commits Spec (Quick Reference)

Format: <type>[optional scope]: <description>

TypeUser impactInclude in changelog?
featNew capability✅ Yes — New Features
fixBug resolved✅ Yes — Bug Fixes
perfFaster/cheaper✅ Yes — Improvements
docsDocumentationMaybe (if public API docs)
refactorNone visible❌ No
testNone visible❌ No
choreNone visible❌ No
ciNone visible❌ No
BREAKING CHANGERequires migration✅ Always — prominently

The key insight: most commits don't belong in a user-facing changelog. A typical sprint might have 40 commits, 6 of which are genuinely user-relevant. Good changelog automation filters aggressively.

The Translation Problem

Here's where most automated changelog tools fall short. They faithfully reproduce the commit message:

# What the tool produces:
## Features
- feat(auth): add Google OAuth provider

## Bug Fixes  
- fix(dashboard): resolve undefined reference on empty state
- fix(billing): handle edge case in proration calculation

This is technically correct but not user-facing. A real product changelog entry reads differently:

## What's New in v2.4.0

✨ **Sign in with Google** — You can now log in or create an account using your Google account. Look for the "Continue with Google" button on the login screen.

🐛 **Dashboard no longer shows a blank screen** for new accounts with no data.

🐛 **Billing: fixed incorrect proration** when upgrading plans mid-cycle.

Getting from the first format to the second requires either manual editing or an additional transformation step.

Tool Option 1: git-cliff

git-cliff is the most flexible changelog generator. It parses conventional commits, supports custom Tera templates, and works with any language.

# Install
cargo install git-cliff
# or: brew install git-cliff

# Generate changelog from last tag to HEAD
git cliff --latest --output CHANGELOG.md

# Generate for a specific range
git cliff v1.0.0..v1.1.0 --output CHANGELOG.md

Custom template example (cliff.toml):

[changelog]
header = """
# Changelog\n
"""
body = """
{% if version %}\
## {{ version | trim_start_matches(pat="v") }} ({{ timestamp | date(format="%Y-%m-%d") }})
{% else %}\
## Unreleased
{% endif %}\
{% for group, commits in commits | group_by(attribute="group") %}
### {{ group | upper_first }}
{% for commit in commits %}
- {{ commit.message | upper_first }}\
{% endfor %}
{% endfor %}\n
"""

[git]
conventional_commits = true
filter_unconventional = true
commit_parsers = [
  { message = "^feat", group = "✨ New Features" },
  { message = "^fix", group = "🐛 Bug Fixes" },
  { message = "^perf", group = "⚡ Performance" },
  { message = "^.*: add", group = "✨ New Features" },
  { message = "^.*", skip = true },
]

Tool Option 2: release-please (GitHub Actions)

If you're on GitHub, release-please automates the entire release flow — not just the changelog. On every push to main, it maintains an open "Release PR" that accumulates changes. When you merge it, it creates the GitHub Release and bumps the version.

# .github/workflows/release-please.yml
name: Release Please
on:
  push:
    branches: [main]

permissions:
  contents: write
  pull-requests: write

jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          token: ${{ secrets.GITHUB_TOKEN }}
          release-type: node

What it does automatically:

  • Parses conventional commits on every push to main
  • Maintains an open PR: "chore: release v1.4.0" with the accumulated changelog
  • On merge, creates the GitHub Release with the changelog body
  • Bumps package.json version following semver from commit types

The User-Facing Gap

Both git-cliff and release-please produce developer-readable changelogs. They're great for GitHub Releases. But they don't solve:

  • In-app "What's New" notifications — showing users new features inside the product itself
  • Email digests — sending a formatted release summary to your customer list
  • Public changelog page — a browsable, SEO-indexed /changelog on your site
  • Slack/Teams announcements — notifying internal teams or customer communities
  • Non-technical language — translating "fix(billing): handle proration edge case" into "Fixed: billing amounts now calculate correctly when upgrading mid-cycle"
The real gap: Automated tools get the raw material right. The last mile — publishing polished notes to users across every relevant channel automatically on every release — still requires custom glue code for most teams.

Building the User-Facing Layer

Option A: GitHub Actions webhook pipeline

name: Publish Changelog
on:
  release:
    types: [published]

jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - name: Post to Slack
        uses: slackapi/slack-github-action@v1
        with:
          payload: |
            {
              "text": "🚀 *${{ github.event.release.name }}* released!\n${{ github.event.release.body }}"
            }
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}

              "from": "releases@yourapp.com",
              "to": ["users@yourapp.com"],
              "subject": "What'\''s new in ${{ github.event.release.name }}",

Common Pitfalls

  • Forgetting breaking changes — always surface BREAKING CHANGE commits prominently, regardless of filtering rules
  • Scope overload — scopes like feat(auth): are useful for filtering but remove them from user-facing notes (users don't think in modules)
  • Including internal commits — chore, test, ci commits add noise; filter them by default
  • Stale GitHub Releases — if your release automation runs but nobody checks GitHub Releases, the changelog exists but users never see it
  • Assuming everyone uses GitHub — in-app notifications and email reach users who never visit your GitHub repo

Summary

Conventional Commits give you the structured input that makes changelog automation tractable. From there, the pipeline looks like:

  1. Enforce conventional commits (commitlint + husky, or PR title rules)
  2. Parse and filter on release (git-cliff, release-please, or custom script)
  3. Translate technical descriptions into user language (manual edit, or LLM-assisted)
  4. Publish to where users actually are: changelog page, in-app, email, Slack

Steps 1–2 are solved. Steps 3–4 are where most teams still have manual work. That's the automation gap worth closing.
