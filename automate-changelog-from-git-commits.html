How to Automate Your Changelog from Git Commits

September 22, 2026 · 8 min read

Writing changelogs manually is one of those tasks that sounds simple but consistently gets skipped. The result: users have no idea what changed between releases, and support tickets pile up asking about "the new version."

This guide covers the practical ways to generate user-facing release notes directly from your git commit history — from simple scripts to fully automated pipelines.

Why Changelogs Get Skipped

Most developers intend to write changelogs. Here's why it doesn't happen:

  • Context switching cost — changelogs require translating technical changes into user language, which takes focused effort right when you're trying to ship
  • No clear audience — internal teams want technical details; end-users want to know if their feature shipped
  • Timing — the PR author knows the context; by release day, they've forgotten half of it
  • Inconsistency — every developer writes in a different style, making changelogs feel fragmented

Automation doesn't solve all of these, but it eliminates the blank-page problem and creates a forcing function.

Method 1: The Raw git log Approach

The simplest starting point is piping git log output into a text file:

git log --pretty=format:"- %s" v1.2.0..v1.3.0 > CHANGELOG.md

This gives you a flat list of commit messages. It's a baseline, not a finished changelog. Raw commit messages like "fix typo in auth service" or "wip: dashboard refactor" are meaningless to end-users.

The improvement requires two things: structured commit messages and a parser that knows what users care about.

Method 2: Conventional Commits

Conventional Commits is a lightweight spec that prefixes commit messages with a type:

feat: add OAuth login with Google
fix: resolve race condition in payment processing
docs: update API authentication guide
chore: upgrade Node.js to v20
refactor: simplify database connection pooling

With this structure, automation becomes straightforward:

  • feat: → "✨ New Features"
  • fix: → "🐛 Bug Fixes"
  • perf: → "⚡ Performance Improvements"
  • Everything else → either filtered out or bucketed as "🔧 Internal Changes"

Method 3: Keyword Heuristics (for messy commit history)

Most real-world repos don't use conventional commits. If your history looks like this:

Refactored the auth middleware
Added dark mode toggle
Fixed the bug where users got logged out
Update README
Merge branch 'feature/billing'

You need keyword-based heuristics to classify commits:

const FEATURE_KEYWORDS = ['add', 'added', 'new', 'implement', 'introduce', 'support'];
const FIX_KEYWORDS = ['fix', 'fixed', 'bug', 'resolve', 'patch', 'correct'];
const IMPROVEMENT_KEYWORDS = ['improve', 'update', 'refactor', 'optimize', 'enhance'];

function classifyCommit(message) {
  const lower = message.toLowerCase();
  if (FEATURE_KEYWORDS.some(k => lower.includes(k))) return 'feature';
  if (FIX_KEYWORDS.some(k => lower.includes(k))) return 'fix';
  if (IMPROVEMENT_KEYWORDS.some(k => lower.includes(k))) return 'improvement';
  return 'other';
}

This isn't perfect — but it transforms a wall of commit messages into something roughly useful in seconds.

Method 4: AI-Assisted Summarization

The latest approach uses LLMs to translate raw commits into plain-English user-facing notes. Given a batch of commits, a model can:

  • Merge related commits into a single changelog entry
  • Drop internal/chore commits that users don't care about
  • Rephrase technical changes in user-facing language
  • Add appropriate emojis or section headers

A basic prompt:

Given these git commits:
  ${commits.join('\n')}

Convert them into user-facing changelog entries.
Group related changes. Skip internal changes (chore, ci, test, docs).
Write in plain English as if addressing the end user.
Format as markdown with sections: New Features, Bug Fixes, Improvements.
The limitation: this works well for structured inputs, less well for one-word commits like "wip" or "fix." Clean inputs produce clean outputs.

Automating the Release Workflow in GitHub Actions

The most robust setup runs changelog generation automatically on every PR merge to main:

name: Generate Changelog
on:
  push:
    branches: [main]

jobs:
  changelog:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Generate changelog
        run: |
          git log --pretty=format:"%s" $(git describe --tags --abbrev=0)..HEAD \
            > /tmp/commits.txt
          # pipe to your parser here

      - name: Commit changelog
        run: |
          git config user.email "bot@example.com"
          git config user.name "Changelog Bot"
          git add CHANGELOG.md
          git commit -m "chore: update changelog [skip ci]" || true
          git push

Publishing to Users

The generated changelog is only valuable if users see it. Common distribution channels:

  • GitHub Releases — auto-create a release with the changelog body
  • Public changelog page — a /changelog route on your marketing site or app
  • Embeddable widget — a floating "What's new" button in your product UI
  • Slack/email digest — push to team channels or external users on each release

Many teams have the git integration sorted but struggle with the last-mile: getting the generated notes in front of users automatically on every release.

Summary

Automating changelogs from git commits is achievable at any codebase maturity level. The core steps:

  1. Get your commits into a parseable format (conventional commits preferred, keyword heuristics as fallback)
  2. Classify and filter commits by user relevance
  3. Generate human-readable entries — or use an LLM for the messy cases
  4. Publish automatically on each release to wherever users will see it

The tooling for steps 1–3 is mature. The gap most teams face is step 4: getting polished notes in front of users without manual work on every release.
